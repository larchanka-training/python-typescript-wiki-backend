# Настройка миграций базы данных с Alembic и PostgreSQL

Этот документ описывает базовую настройку миграций базы данных в Python-проекте с использованием SQLAlchemy, Alembic и PostgreSQL.  

Документация объясняет, какие изменения были внесены в проект, зачем они нужны и как проверить, что миграции работают корректно в Docker-окружении.

## Что было сделано

В проект добавлена базовая инфраструктура для работы с PostgreSQL и миграциями:

- Подключены зависимости для работы с БД и миграциями:
  - SQLAlchemy — ORM и работа с БД
  - Alembic — управление миграциями
  - psycopg — драйвер PostgreSQL
- Инициализирован Alembic:
  - Добавлен конфигурационный файл
  - Настроен `env.py` для работы с SQLAlchemy `Base`
- Создана первая миграция:
  - Таблица `tmp` с полем `id`
- Добавлена миграция для пользователей (/token):
  - `0002_create_users_table` — таблица `users` с `telegram_id` (unique), профилем и timestamps
  - `0003_add_last_login_at` — добавлен `last_login_at`, `username` стал nullable
- Добавлена миграция для сессий (/session):
  - `0004_create_sessions_table` — таблица `sessions` с `token_hash`, `expires_at`, `revoked_at`
- Обновлён `.gitignore`:
  - Исключены Python cache-файлы
  - Удалены случайно закоммиченные `.pyc`

## Используемые инструменты

### PostgreSQL
Основная база данных проекта при локальной разработке. Запускается в Docker через `docker-compose`.

### SQLAlchemy
Используется для описания моделей и генерации метаданных, которые Alembic применяет при создании миграций.

### Alembic
Отвечает за:
- создание миграций;
- применение изменений схемы БД;
- хранение текущей версии схемы в таблице `alembic_version`.

## Структура Alembic

### env.py

Файл отвечает за конфигурацию Alembic и связывает его с SQLAlchemy:

- Используется единый `Base.metadata` из приложения;
- Поддерживаются online и offline режимы миграций;
- Все модели импортируются заранее, чтобы Alembic «видел» их при автогенерации;
- Включена опция `compare_type`, чтобы отслеживать изменения типов колонок.

### script.py.mako

Шаблон для генерации файлов миграций:

- Содержит стандартную структуру `upgrade` и `downgrade`;
- Используется Alembic автоматически при создании новых ревизий;
- Не требует ручных изменений в большинстве случаев.


## Таблица users

Таблица используется для upsert пользователя при проверке токена.

Поля:
- `id` (pk)
- `telegram_id` (unique)
- `username`
- `first_name` (nullable)
- `last_name` (nullable)
- `photo_url` (nullable)
- `permission` (nullable)
- `created_at` (default `now()`)
- `updated_at` (default `now()`)
- `last_login_at` (default `now()`)

## Таблица sessions

Таблица используется для stateful сессий.

Поля:
- `id` (uuid, pk)
- `user_id` (fk → users.id)
- `token_hash` (unique) — hash от session token (raw токен в БД не хранится)
- `expires_at`
- `revoked_at` (nullable)
- `created_at` (default `now()`)
- `updated_at` (default `now()`)

## Миграции для /token

- `0002_create_users_table` — создаёт таблицу `users`, уникальный `telegram_id`, профильные поля и timestamps.
- `0003_add_last_login_at` — добавляет `last_login_at` и делает `username` nullable.

## Миграции для /session

- `0004_create_sessions_table` — создаёт таблицу `sessions` и индексы (`user_id`, `expires_at`, `revoked_at`).

## Команды Alembic

```bash
alembic revision --autogenerate -m "message"
alembic upgrade head
alembic downgrade -1
alembic current
alembic history
```

Если БД запускается через docker compose, можно вызывать Alembic внутри контейнера `api`:
`docker compose exec api alembic upgrade head`.

## Идемпотентность и upsert

- Уникальность `telegram_id` обязательна для корректной работы `INSERT ... ON CONFLICT`.
- `last_login_at` обновляется при каждом успешном verify, `created_at` задаётся только при создании.


## Проверка работы миграций

Для проверки корректности настройки выполните следующие шаги:

1. Запустите сервисы:
   - `docker compose up -d`

2. Примените миграции:
   - `docker compose exec api alembic upgrade head`

3. Проверьте таблицы через psql:
   - Подключитесь к базе `wiki`
   - Выполните команду просмотра таблиц

4. Проверьте через pgAdmin:
   - Databases → wiki
   - Schemas → public → Tables
