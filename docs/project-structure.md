# Общая структура папок проекта

## Краткое описание

Этот документ описывает, **где что лежит в репозитории** и **куда добавлять новые файлы**. Он нужен, чтобы команда поддерживала единый порядок: код не складывался в `main.py`, миграции не терялись, а мок-данные не попадали в прод.

Здесь указано назначение основных папок и простые правила, которые помогают не “сломать” структуру проекта.

## 1. Структура репозитория

Ниже — рекомендуемая общая структура (часть файлов уже есть в проекте):

```text
/
  app/                      # исходный код FastAPI приложения
  alembic/                  # миграции БД (Alembic)
  tests/                    # тесты и фикстуры (рекомендуется добавить)
  scripts/                  # скрипты для dev/maintenance (рекомендуется добавить)
  mock_oauth/               # локальный oauth.name token issuer (для Docker)
  docs/                     # проектная документация (рекомендуется добавить)

  .env.example              # пример переменных окружения
  .gitignore
  .pre-commit-config.yaml   # pre-commit хуки
  alembic.ini               # конфиг Alembic
  docker-compose.yml
  docker-compose.mock.yml   # override для локального oauth.name mock
  Dockerfile
  pyproject.toml            # настройки инструментов (ruff/formatters и т.п.)
  requirements.txt          # зависимости (если используете pip requirements)
  README.md                 # как запустить проект
```

Что **не коммитим**:

- `.venv/` — локальное виртуальное окружение
- `.ruff_cache/` — кэш линтера

## 2. Исходники приложения (`app/`)

Папка `app/` — это Python-пакет с кодом бэкенда.

### 2.1. Минимум (как часто бывает на старте)

- `app/main.py` — точка входа FastAPI (создание приложения, подключение роутов)
- `app/db.py` / `app/models.py` — допустимо на старте, но со временем лучше разнести по папкам

### 2.2. Рекомендуемая структура для роста проекта

Когда endpoints и логики станет больше, используем разделение по слоям:

```text
app/
  main.py                   # создание FastAPI приложения, подключение роутов
  api/                      # HTTP слой (эндпоинты и схемы)
    v1/
      routes/               # роутеры по доменам: auth.py, users.py и т.д.
      schemas/              # Pydantic схемы запросов/ответов
  services/                 # бизнес-логика (use-cases), не завязана на HTTP
    token_service.py        # decrypt + TTL для oauth.name токена
  repositories/             # работа с БД (CRUD/queries), чтобы не писать запросы в роутерах
  db/                       # всё про базу
    session.py              # engine + sessionmaker
    base.py                 # declarative Base
    models/                 # SQLAlchemy модели по файлам
  clients/                  # клиенты внешних сервисов (3rd party API)
  core/                     # конфиг, логирование, обработчики ошибок
  utils/                    # небольшие утилиты (без бизнес-логики)
```

Принцип простой:

- **Роуты** принимают запрос → вызывают **service** → service использует **repository/client** → возвращаем ответ.

## 3. База данных и миграции (`alembic/`)

`alembic/` отвечает за версионирование схемы БД.

```text
alembic/
  env.py
  script.py.mako
  versions/                 # файлы миграций
alembic.ini
```

Правило:

- Любое изменение таблиц делаем **через новую миграцию** в `alembic/versions/`.
- Не правим схему БД вручную “в обход” миграций.

## 4. Тесты и мок-данные (`tests/`)

Рекомендуется добавить папку `tests/`, даже если тестов пока мало. Это сразу задаёт порядок.

```text
tests/
  unit/                     # модульные тесты (быстрые)
  integration/              # интеграционные тесты (БД/внешние сервисы)
  fixtures/                 # мок-данные (json/тексты/заготовки)
  conftest.py               # общие фикстуры (если используете pytest)
```

Правило:

- Мок-данные для тестов храним в `tests/fixtures/`, а не в `app/` и не в корне репозитория.

---

## 5. Скрипты для разработки (`scripts/`)

Папка `scripts/` — для задач “один раз/иногда”, которые не являются частью приложения:

```text
scripts/
  seed_dev.py               # наполнение dev БД данными
  backfill_*.py             # разовые миграции данных
  local_tools_*.py          # локальные проверки/утилиты
```

Правило:

- Скрипты не должны быть импортируемой частью приложения. Это отдельные запускные файлы.

---

## 6. Документация (`docs/`)

Документацию лучше держать рядом с кодом, чтобы она обновлялась вместе с проектом.

```text
docs/
  project-structure.md      # этот документ
  api.md                    # список эндпоинтов и их назначение
  errors.md                 # единый формат ошибок и коды ответов
  adr/                      # архитектурные решения (коротко: что решили и почему)
```

## 7. Правила и договорённости

1. **Не складываем всё в `main.py`.**  
   `main.py` — это “сборка” приложения: подключение роутов, middleware, обработчики ошибок.

2. **Бизнес-логика живёт в `services/`.**  
   Если логика не про HTTP (не про request/response) — ей место там.

3. **Доступ к БД через `repositories/`.**  
   Роуты не должны содержать большие SQLAlchemy-запросы.

4. **Миграции только через Alembic.**  
   Любые изменения схемы — отдельной миграцией в `alembic/versions/`.

5. **Мок-данные и тестовые заготовки — только в `tests/fixtures/`.**  
   Никаких “test_data.json” в корне или внутри `app/`.

6. **Документируем важные договорённости.**  
   Формат ошибок, правила именования, структура — фиксируем в `docs/`, а не “в чате”.
